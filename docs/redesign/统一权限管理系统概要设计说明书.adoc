== 引言与总体设计

=== 编写目的与背景

本文说明统一权限管理系统的总体结构、模块协作、接口、全局数据、部署与质量属性评估，用于大作业二评审及代码实现。需求与详细设计合订本保存当前基线的功能详述和字段字典。

本次设计承接 v3.2.2 并按 2026-11-17 确认决定修订。平台自身和老师课程管理系统作为两个接入系统，统一使用 RBAC 授权。

=== 设计原则与约束

RBAC 表达全部操作许可，部门限定账号、角色及管理范围。结构化与 DDD 采用一个分层架构下的两种业务实现，共用 API、数据契约及 Infrastructure。接口按资源划分，敏感字段采用白名单。

当前业务为单项维护、授权和两个系统接入。部署保留已有服务器服务。性能以当前资源实测建立基线，组号由提交打包参数补齐。

=== 架构故事

以下四个场景分别对应效用树叶节点。安全使用确定的拒绝要求，可修改性使用配置切换与相同契约验证；性能和恢复时长先测量，结果随基线报告归档。


==== S1 安全 U-S1

管理员撤销课程审核权限后，教师继续使用原登录令牌提交审核。平台依据已提交的 RBAC 关系拒绝该次操作，课程数据保持原值。 对应 REQ-N-01。

[cols="2,7",options="header"]
|===
|ATAM 要素 |内容
|刺激源 |具有有效课程令牌的教师
|刺激 |管理员撤销 CR 后发起新审核请求
|环境 |正常运行，撤销事务已经提交
|制品 |身份鉴权、授权关系和课程审核入口
|响应 |查询当前权限，返回拒绝并保留课程原状态
|响应度量 |撤权提交后的测试请求全部返回 403；越权成功数为 0
|===


==== S2 性能 U-P1

在相同用户与授权数据上逐级增加并发权限查询，平台通过连接池及索引执行查询，分别记录两套实现的响应分布和资源使用。 对应 REQ-N-02。

[cols="2,7",options="header"]
|===
|ATAM 要素 |内容
|刺激源 |负载发生器
|刺激 |相同请求组合逐级增加并发
|环境 |与部署说明相同的资源限制及日志级别
|制品 |Bearer 认证、授权查询和数据库连接池
|响应 |完成查询，记录吞吐、延迟、错误和内存
|响应度量 |按负载记录 P50、P95、吞吐量及错误率；实测结果建立回归基线
|===


==== S3 可用性 U-A1

应用进程退出后，Swarm 重启应用。未过期且未撤销的令牌通过原签名密钥和数据库会话继续验证；依赖中断时拒绝受控操作。 对应 REQ-N-03。

[cols="2,7",options="header"]
|===
|ATAM 要素 |内容
|刺激源 |运行平台或故障注入脚本
|刺激 |应用进程退出或身份依赖暂时不可用
|环境 |数据库卷和签名密钥仍可用
|制品 |Swarm 任务、签名配置、数据库会话
|响应 |进程恢复后验证原会话；依赖故障返回 503
|响应度量 |记录首次失败请求至首个成功请求的秒数；原有效会话恢复成功，故障期间越权成功数为 0
|===


==== S4 可修改性 U-M1

开发者把业务配置从 structured 改为 ddd 并重启应用。管理前端、外部课程系统及数据库结构保持相同契约，重复执行既有验收。 对应 REQ-N-04。

[cols="2,7",options="header"]
|===
|ATAM 要素 |内容
|刺激源 |开发者
|刺激 |更换业务策略配置
|环境 |相同镜像、相同数据库和接口
|制品 |用例端口、装配配置及两套业务服务
|响应 |仅装配选定实现，重复执行相同契约
|响应度量 |API、数据库迁移及前端修改数为 0；两套配置的共同契约用例全部通过
|===

==== 评估发现

[cols="2,7",options="header"]
|===
|类型与编号 |决策、论证及质量影响
|风险 R-01 |AD-05 使用单实例 MySQL；实例失效会中断认证和业务读写；降低节点故障期间的可用性。
|风险 R-02 |AD-06 两个 JVM 同置管理节点；节点失效同时影响入口和应用；应用进程重启不能覆盖节点损失。
|风险 R-03 |AD-03 同步实时鉴权；数据库或身份网络变慢会增加课程调用等待；影响 P95 与吞吐。
|非风险 N-01 |AD-04 在数据库保存撤销记录，权限保存在当前 RBAC 关系；应用重启和旧令牌不会恢复已撤销权限。
|非风险 N-02 |AD-01、AD-02 两套实现共用契约和存储约束，配置切换可用同一套测试验证。
|敏感点 SENS-01 |数据库连接池上限和 SQL 索引显著影响请求排队及 P95。
|敏感点 SENS-02 |签名密钥持久化与数据库卷直接决定应用重启后的令牌及会话可验证性。
|权衡 T-01 |实时查权限提高撤权及时性，同时增加数据库访问量。
|权衡 T-02 |有限服务器上使用单副本降低内存占用，同时保留入口和数据库单点。
|===

=== GRASP 职责分配与双实现

以 ROLE-11 新增继承为抽查入口。RoleController 校验正整数路径，取得操作者，交给 RoleUseCase；业务实现先检查 role.manage，在事务内锁定部门并核对两端归属，再判断继承图并写入关联。ManagementStore 隔离业务与 SQL，JdbcManagementStore 锁定部门并写入继承边。


[cols="3,7",options="header"]
|===
|原则 |代码位置与职责
|Controller |RoleController 接收 HTTP，StructuredRoleService 或 DddRoleService 编排事务；不把业务防环放到 HTTP 层。
|Information Expert |RoleHierarchy 接收当前继承边，执行 requireAcyclic；User 根据自身部门校验可分配的角色。
|Creator |DddUserService 根据当前用户资料创建 User，交由 User 校验目标角色的部门。
|Low Coupling |API 依赖 RoleUseCase，业务依赖 ManagementStore；领域规则使用 Java 集合，与 Spring JDBC、HTTP 解耦。
|High Cohesion |Controller 处理输入输出，Service 处理事务与范围，RoleHierarchy 处理无环规则，适配器处理 SQL。
|Polymorphism |五个用例端口分别有 Structured 与 Ddd 实现，启动条件只装配配置选中的实现。
|Indirection |RoleUseCase 与 ManagementStore 分开调用方和实现方，便于契约测试与替换。
|Pure Fabrication |JdbcManagementStore 读写直接关系；JdbcEffectiveAccessStore 集中递归查询；AccessPolicy 检查权限及部门边界。
|Protected Variations |共享 API、Data 和存储端口保护两种业务实现变化；同一契约套件验证外部行为。
|===

[cols="2,5,5",options="header"]
|===
|比较项 |结构化实现 |DDD 实现
|业务规则位置 |StructuredRoleService 在事务脚本中调用共享防环规则并写入继承边。 |DddRoleService 编排事务和范围，调用同一领域规则判断环。
|已有授权修改 |Service 校验权限和范围，数据库拒绝重复分配。 |User 校验角色部门，应用服务保存关联，数据库拒绝重复分配。
|继承图生命周期 |事务读取 Data.Inheritance 边列表。 |同一份列表作为规则输入，队列和已访问集合在方法结束后释放。
|共同部分 |API、认证、用例端口、数据库迁移、JDBC、日志及页面。 |相同契约和基础设施，不复制两套数据库与接口。
|配置切换 |BACKEND_STRATEGY=structured。 |BACKEND_STRATEGY=ddd，重启生效。
|===

== 接口设计

=== 外部接口

用户界面为桌面浏览器 Web 页面，提供列表、表单及授权选择；两种后台策略使用同一套界面。浏览器使用鼠标、键盘和屏幕输入输出。

硬件接口：本章节不适用，原因：当前系统通过浏览器与服务器网络通信，不接入专用硬件设备。

第三方软件接口为老师课程管理系统，使用 HTTP/JSON 和 Authorization Bearer。课程前端向平台申请目标系统令牌，课程后端验签并查询当前身份和操作许可。对应 REQ-F-07、AD-07。


界面权限与 API 权限共用 RBAC 关系并分别授权。界面使用独立菜单和按钮码，无权限控件 disabled；接口按 operationId 对应的 API 码及对象规则决定是否执行。授权表单使用三个只读候选查询，避免依赖无关目录管理权限。课程页面初始化还调用 GET /course-api/me，读取与平台 userId 关联的本地教师资料和当前界面权限；未关联时返回 403。


[cols="2,5,3,3",options="header"]
|===
|外部接口编号 |路径 |核心输入 |核心输出
|EXT-01 |POST /auth/login |用户名、手机号和目标系统 |Bearer 凭据及有效期
|EXT-02 |GET /auth/me |Bearer |当前身份、角色、当前系统界面码
|EXT-03 |GET /auth/permissions/{permission} |Bearer 与独立界面码 |allowed
|EXT-04 |GET /auth/api-permissions/{operationId} |Bearer 与操作编号 |allowed
|EXT-05 |GET /auth/users/{userId} |Bearer 与用户标识 |用户标识、工号和姓名
|EXT-06 |POST /auth/logout |Bearer |撤销结果
|EXT-07 |GET /auth/departments |Bearer、parentId、keyword、分页 |部门及展开提示
|EXT-08 |GET /auth/departments/{departmentId}/users |Bearer、departmentId、keyword、分页 |身份候选人
|===

=== 存储与物理策略

MySQL InnoDB 保存业务数据和登录会话，利用事务、外键及唯一约束维护关系一致性。平台与课程系统使用不同数据库和账号。当前采用单实例，不设置读写分离、分片或额外缓存；实体编号由数据库自增生成，登录会话使用随机 UUID。

授权从数据库当前关系查询，避免缓存失效改变撤权语义。用户、角色列表按部门及分页读取；关联索引用于当前权限查询。数据库连接池有界，性能场景在相同数据与配置下测量。

备份保存两个数据库及迁移版本，签名密钥独立保管。恢复先在临时数据库核对表数、记录及授权关系，再记录恢复结果。引用关系和技术会话均在备份范围内。
