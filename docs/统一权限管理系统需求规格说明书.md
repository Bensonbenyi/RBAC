## 1 引言

### 1.1 编写目的

本文档明确统一权限管理系统的业务范围、参与者、业务规则、功能需求、数据流、操作流程和验收指标，为后续设计、开发和测试提供依据。

本文档只描述需求。代码结构、数据库结构、接口地址、通信协议和接口字段不在本文档范围内。

### 1.2 项目背景

集团现有多个由不同开发商建设和维护的业务系统。各系统分别保存账号、角色和权限，员工需要在不同系统注册账号，管理人员也需要进入各系统单独授权。集团无法集中查看员工拥有哪些业务系统权限，也无法统一完成开户、授权、撤权和审计。

本项目建设一个统一权限管理系统。平台集中维护组织、员工、外部系统、权限目录和角色，由最高管理员或部门管理员为员工分配外部系统角色。平台将账号和授权结果下发到外部系统，并记录同步状态和管理操作。

当前资料列出 17 个外部业务系统和 1 个本平台对应的“系统管理后台”。本期以 17 个外部系统为初始范围，后续可继续接入新系统。

### 1.3 定义

| 术语 | 定义 |
| --- | --- |
| 平台 | 本文所述统一权限管理系统。 |
| 外部系统 | 由其他开发商建设和维护、接收平台账号及授权结果的业务系统。 |
| 公司 | 组织结构第一层，包括总公司和 9 个分公司。 |
| 部门 | 公司下的末级管理单元，不再设置下级部门。 |
| 最高管理员 | 平台内置管理角色，可管理全部组织、员工、管理员、外部系统、角色、授权和审计数据。 |
| 部门管理员 | 平台内置管理角色，只能管理其所属部门内的员工、外部角色和授权。 |
| 员工 | 被分配外部系统角色的对象。普通员工不登录平台。 |
| 外部角色 | 某个外部系统内的一组权限。角色只属于一个外部系统。 |
| 权限项 | 外部系统中一个“功能点 + 操作动作”的组合，例如“发文拟稿 + 编辑”。 |
| 有效权限 | 员工当前角色包含且未被外部系统停用的权限项。 |
| 同步任务 | 平台向外部系统发送开户、资料更新、授权、换角、撤权或停用要求，并跟踪处理结果的业务记录。 |
| RBAC0 | 基础角色访问控制模型。权限配置给角色，员工通过角色取得权限，不直接取得单项权限。 |

需求用例编号格式为 `UPMS-REQ-<业务域>-<序号>`。

| 业务域 | 代码 | 范围 |
| --- | --- | --- |
| 身份认证 | AUTH | 管理员登录、退出 |
| 组织管理 | ORG | 公司和部门维护 |
| 员工管理 | EMP | 员工新增、修改、停用和部门调整 |
| 管理员管理 | ADM | 最高管理员和部门管理员任命 |

| 同步管理 | SYNC | 外部账号与授权同步、失败重试 |
| 查询 | QUERY | 角色、权限和同步状态查询 |
| 审计 | AUDIT | 登录日志、操作日志和同步日志 |

## 2 任务概述

### 2.1 目标

平台应完成下列目标：

1. 集中维护公司、部门和员工资料，以唯一用户名和唯一手机号识别员工。
2. 集中登记外部系统，并建立部门与外部系统的一对一绑定关系。
3. 接收外部系统上报的权限目录，以“功能点 + 操作动作”管理权限项。
4. 允许管理员建立外部角色并配置角色权限，员工只能通过角色取得权限。
5. 为员工首次授权时自动创建外部账号，并在角色变更、撤权、资料变更或停用时同步更新外部系统。
6. 展示每次同步的状态。失败任务自动重试，并允许管理员手工重试。
7. 集中记录登录、配置、授权、撤权和同步操作，支持查询与导出。

### 2.2 运行环境

平台采用桌面浏览器访问方式，应支持当前主流桌面版 Google Chrome 和 Microsoft Edge。管理页面按桌面端使用设计，本期不要求适配手机和平板。

平台只面向最高管理员和部门管理员开放登录。普通员工在外部系统中开展业务，不进入本平台。

### 2.3 条件与限制

#### 2.3.1 组织和数据基线

1. 组织结构只有“公司、部门”两层。公司包括总公司和 9 个分公司，共 10 个公司；部门共 101 个，部门下不再设置组织节点。
2. 初始化员工为 10,000 人。用户名和手机号分别唯一，均为必填信息。
3. 当前初始化的外部系统共 17 个：OA 协同办公系统、企业即时通讯系统、企业知识库管理系统、人力资源管理系统、财务管理系统、工程项目管理系统（PMIS）、招投标管理系统、物资设备管理系统、移动巡检 APP、工地 AI 视频监控系统、GIS 地下管线管理系统、企业档案管理系统、车辆管理系统、企业宣传平台、安全生产管理系统、合同全生命周期管理系统和成本管控系统。
4. 权限清单中的“系统管理后台”用于校验本平台的需求范围，不作为外部系统导入。
5. 权限清单中的“系统管理员、公司领导、部门经理、项目经理、普通员工”作为每个外部系统的初始角色。`全部`表示该角色包含本系统全部权限项，`无`或空值表示不包含权限。资料中的 `view`按`查看`处理。

#### 2.3.2 业务限制

1. 一个部门最多绑定一个外部系统，一个外部系统最多绑定一个部门。部门和外部系统均允许暂未绑定。
2. 未绑定部门的员工不能取得外部角色；未绑定部门的部门管理员仍可维护本部门员工。
3. 平台自身只设最高管理员和部门管理员两种固定角色，不允许新建或修改平台角色的权限定义。
4. 最高管理员人数不限。每个部门可任命多名部门管理员。
5. 每名员工在所属部门绑定的外部系统中最多拥有一个角色。分配新角色会替换旧角色。
6. 部门管理员只能处理本部门数据。最高管理员可以处理任意部门数据，并可代替部门管理员执行角色和授权操作。
7. 跨部门调动采用人工协作流程。原部门先撤权，最高管理员再修改员工所属部门，新部门最后重新授权。平台不自动继承或匹配同名角色。
8. 存在有效角色时不得直接调整员工所属部门。存在员工授权时不得直接解除部门与外部系统的绑定。

#### 2.3.3 项目限制

本项目为课程 Demo。管理员登录采用“用户名 + 手机号”同时校验，不设置密码，不发送短信验证码。本期不要求密码策略、双因素认证、多活容灾、工业级监控、备份恢复和生产合规能力。

## 3 数据描述

### 3.1 领域模型

领域模型描述业务概念及其关系，不表示数据库表、字段或存储结构。

![图 3-1 领域模型](assets/domain-model.svg)

图 3-1 领域模型

主要关系如下：

1. 公司包含多个部门，员工属于一个部门。
2. 员工可被任命为最高管理员或本部门的部门管理员。管理员身份决定能否登录平台及其管理范围。
3. 部门与外部系统为可空的一对一绑定关系。
4. 外部系统提供多个权限项，并拥有多个外部角色。角色由若干权限项组成。
5. 员工在所属部门绑定的外部系统中最多拥有一个角色。
6. 员工资料或角色发生变化时产生同步任务。同步任务记录目标外部系统和处理状态。
7. 登录、数据维护、授权和同步操作产生审计记录。

### 3.2 上下文数据流

![图 3-2 上下文数据流图](assets/data-flow-context.svg)

图 3-2 上下文数据流图

最高管理员向平台提交全局管理操作并取得全局查询结果。部门管理员提交本部门员工、角色和授权操作，只能取得本部门结果。外部系统向平台上报权限目录和同步结果，平台向外部系统发送账号及角色变更要求。

### 3.3 一级数据流

![图 3-3 一级数据流图](assets/data-flow-level1.svg)

图 3-3 一级数据流图

一级数据流划分为五类处理：

1. 身份与范围校验：校验用户名、手机号、管理员状态和管理范围。
2. 基础数据管理：维护公司、部门、员工、管理员、外部系统和绑定关系。
3. 权限与角色管理：接收权限目录，维护外部角色和角色权限。
4. 授权与同步：分配、替换或撤销员工角色，并驱动外部账号及授权同步。
5. 查询与审计：查询有效权限、同步状态及审计记录，并导出审计结果。

图中的数据存放区表示需求层面的信息集合，不表示数据库或文件设计。

### 4.2 功能描述

#### 4.2.1 管理员登录与退出

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UPMS-REQ-AUTH-001 |
| 用例名称 | 管理员登录与退出 |
| 级别 | 用户目标 |
| 包 | 身份认证 |
| 参与者 | 最高管理员、部门管理员 |
| 描述 | 管理员使用本人用户名和手机号进入平台，或结束当前会话。 |
| 触发事件 | 管理员打开登录页、提交登录信息或选择退出。 |

#### 4.2.5 外部系统维护

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UPMS-REQ-SYS-001 |
| 用例名称 | 维护外部系统及部门绑定 |
| 级别 | 用户目标 |
| 包 | 外部系统 |
| 参与者 | 最高管理员 |
| 描述 | 最高管理员登记、修改、启停外部系统，并设置其唯一绑定部门。 |

## 5 性能需求

### 5.1 数据准确性

1. 用户名和手机号必须分别保持唯一。新增和修改均执行唯一性校验。
2. 部门与外部系统的一对一关系不得出现重复绑定。
3. 每名员工在其部门外部系统中最多有一个目标角色。
4. 有效权限必须来源于员工当前角色，且权限项和角色均处于有效状态。
5. 同步重试不得重复创建外部账号、重复添加角色或恢复已经撤销的权限。
6. 平台目标状态和外部生效状态不一致时，必须显示差异和最近失败原因，不得将未确认结果显示为已生效。
7. 批量授权和撤权需保留逐人结果，不能用整批成功掩盖部分失败。

### 5.2 时间特性

1. 平台支持至少 100 名管理员同时在线操作。
2. 在规定数据规模和正常网络条件下，至少 95% 的常用页面查询、详情查看和单项管理操作应在 3 秒内返回结果。
3. 外部系统可用且正常响应时，开户、授权、换角、撤权和账号停用应在管理员提交后 3 秒内生效。
4. 批量操作应在 3 秒内返回已受理结果，并持续显示逐人处理状态；批量任务不以全部外部系统处理完成作为页面响应前提。
5. 本期的 10,000 人指标表示员工数据规模，不表示 10,000 名员工并发登录平台。

### 5.3 适应性

1. 平台应允许在现有 17 个外部系统基础上继续登记新系统，不应以固定系统数量限制功能。
2. 新外部系统接入后，可以独立上报权限目录、建立角色并与一个部门绑定。
3. 不同外部系统可以提供不同的功能模块、功能点和操作动作，平台不得要求所有系统使用同一权限集合。
4. 外部权限目录增加、修改或停用时，不应要求修改平台角色模型。
5. 组织、员工和系统数量增加时，原有管理范围和审计规则保持不变。

## 6 运行需求

### 6.1 软件接口

本节只规定平台和外部系统交换信息的业务责任。具体协议、地址、字段、鉴权方式和错误码由后续接口设计文档确定。

| 方向 | 业务信息 | 触发时机 | 结果要求 |
| --- | --- | --- | --- |
| 外部系统到平台 | 权限目录新增、修改、停用 | 外部系统权限目录发生变化 | 平台返回接收结果，重复上报不产生重复权限。 |
| 平台到外部系统 | 外部账号开户和角色分配 | 员工首次取得角色 | 外部系统创建账号并返回授权结果。 |
| 平台到外部系统 | 员工资料更新 | 已授权员工的姓名、用户名、手机号或状态变化 | 外部系统更新账号资料并返回结果。 |
| 平台到外部系统 | 角色替换或角色权限更新 | 员工换角、角色权限变化、权限项停用 | 外部系统按平台当前目标状态更新权限。 |
| 平台到外部系统 | 撤权和账号停用 | 管理员撤权或员工停用 | 外部系统移除权限并停用账号。 |
| 外部系统到平台 | 同步成功、失败和失败原因 | 外部系统完成或拒绝处理 | 平台更新任务状态、生效时间和失败原因。 |

### 6.2 故障处理

1. 外部系统无响应、网络异常或返回失败时，平台保留业务目标和同步任务，状态设为待同步或同步失败。
2. 平台按任务当前目标状态自动重试。管理员可在权限范围内查看失败原因并人工重试。
3. 若重试前员工、角色、权限项或系统状态已变化，平台应执行最新目标状态，不得恢复过期授权。
4. 同一业务目标的重复发送和重复返回不得生成重复账号、角色或审计记录。
5. 外部系统目录上报失败时，平台保留上一次已确认目录，不使用不完整目录覆盖有效数据。
6. 批量任务部分失败时，成功项保持成功，失败项独立重试，并向管理员展示逐项结果。
7. 平台操作失败时不得留下违反唯一性、一对一绑定或单角色限制的中间状态。

## 7 其它需求

### 7.1 可用性

1. 列表页面应支持按常用标识筛选，并明确显示对象状态和同步状态。
2. 批量授权、角色替换、撤权、停用和解绑等影响访问权的操作必须显示目标范围并要求确认。
3. 页面应区分“平台目标状态”“待同步”“同步失败”和“已生效”，不得只显示一个笼统的成功状态。
4. 失败提示应说明可处理的原因和下一步操作；管理员可进入同步任务查看详细结果。

### 7.2 权限隔离

1. 最高管理员可访问全部数据和功能。
2. 部门管理员只能访问本部门员工、本部门绑定系统、该系统角色、授权和同步记录。
3. 页面筛选、详情查看、导出和批量操作均执行相同的范围校验。
4. 修改请求中的部门、员工或系统不在管理员范围内时，平台拒绝整个请求并记录越权尝试。
5. 管理员身份取消、员工停用或部门范围变化后，原会话不得继续取得已失效权限。

### 7.3 审计与可追溯性

1. 登录成功、登录失败、退出、组织和员工变更、管理员任命、系统绑定、权限目录更新、角色变更、授权撤销、同步和重试均需记录。
2. 审计记录至少包含操作者、时间、管理范围、业务对象、操作类型、操作前内容、操作后内容和结果。
3. 外部同步记录需关联原始管理操作，并保留每次尝试、返回结果和最终状态。
4. 管理员不能修改或删除审计记录。部门管理员只能查看和导出本部门记录。

### 7.4 验收要点

1. 使用初始化资料装载 10 个公司、101 个部门、10,000 名员工和 17 个外部系统，验证员工与组织归属正确。
2. 验证用户名或手机号重复时无法新增或修改员工。
3. 验证普通员工不能登录；管理员用户名和手机号不匹配时不能登录。
4. 验证部门管理员无法查询、修改、导出或批量处理其他部门数据。
5. 验证同一部门或同一外部系统不能重复绑定，存在有效授权时不能直接解绑。
6. 验证员工只能拥有一个角色，分配新角色必须提示并替换旧角色。
7. 验证首次授权触发开户，撤权和员工停用触发外部账号停用。
8. 验证权限项停用后不再出现在有效权限中，并触发受影响员工的权限更新。
9. 验证同步失败不会显示为已生效，自动和人工重试不会产生重复账号或重复授权。
10. 验证跨部门调动必须先撤权，调动后由新部门重新授权。
11. 验证审计记录覆盖登录、配置、授权、撤权和同步操作，并能按权限范围查询和导出。
12. 在 10,000 名员工、17 个外部系统和 100 名并发管理员的测试条件下，验证常用操作和授权生效时间符合第 5.2 节要求。
